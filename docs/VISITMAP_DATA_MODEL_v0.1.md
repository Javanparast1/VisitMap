# VisitMap — طراحی اجرایی مدل داده محلی v0.1

> این سند برای پیاده‌سازی اولیه Room در شاخه `feat/room-local-database` تهیه شده است. اسناد محصول v0.4 و اصلاحیه v0.5 همچنان مرجع بالادستی هستند.

## 1. تصمیم‌های پایه

- پایگاه داده در فضای خصوصی اپلیکیشن و روی دستگاه باقی می‌ماند.
- شناسه‌ها به‌صورت UUID و در SQLite به شکل TEXT ذخیره می‌شوند.
- زمان‌ها به‌صورت Unix epoch milliseconds ذخیره می‌شوند؛ نمایش محلی فقط در لایه ارائه انجام می‌شود.
- مختصات به‌صورت REAL و دقت به متر به‌صورت REAL nullable ذخیره می‌شود.
- وضعیت، نوع مشتری و منبع مکان با رشته‌های ثابت ذخیره می‌شوند تا مقدارهای ذخیره‌شده خوانا و قابل مهاجرت باشند.
- حذف فیزیکی مشتری در DAO ارائه نمی‌شود؛ غیرفعال‌سازی با تغییر status انجام می‌شود.
- هیچ migration مخرب یا fallback به حذف پایگاه داده مجاز نیست.

## 2. جداول

### customers
یک رکورد برای هر فروشگاه فیزیکی مستقل:
- customerId (UUID, primary key)
- name (required)
- customerType: SUPERMARKET یا TOBACCONIST
- phone، contactName و description اختیاری
- status: ACTIVE یا INACTIVE
- createdAt و updatedAt

شاخص‌ها: name، customerType، status، contactName و phone.

### customer_locations
فقط موقعیت جاریِ تأییدشده برای هر مشتری؛ customerId هم‌زمان primary key و foreign key است. بنابراین در نسخه اول برای هر فروشگاه حداکثر یک موقعیت جاری وجود دارد. تا پیش از تأیید اولین پیشنهاد، مشتری می‌تواند هیچ رکوردی در این جدول نداشته باشد.

فیلدها: latitude، longitude، accuracyMeters، provider، capturedAt، isManual و اطلاعات جغرافیایی اختیاری province/county/city/neighborhood.

### location_observations
ثبت مستقل پیشنهادهای مکان‌یابی برای جلوگیری از مخلوط شدن «موقعیت دریافتی» با «موقعیت تأییدشده». هر مشاهده به یک مشتری متصل است و reviewStatus آن یکی از PENDING، ACCEPTED یا REJECTED است. **اولین موقعیت و تمام موقعیت‌های بعدی ابتدا پیشنهاد هستند و هیچ‌کدام بدون تأیید دستی کاربر موقعیت معتبر محسوب نمی‌شوند.**

این جدول در این مرحله یک رکورد برای هر تلاش/انتخاب مکان ذخیره می‌کند؛ نه تمام نمونه‌های پیوسته GPS در طول زمان. نگهداری جریان خام GPS خارج از دامنه نسخه اول است.

### location_history
هر بار که موقعیت جاری پذیرفته‌شده تغییر می‌کند، snapshot قبلی و جدید در این جدول ثبت می‌شود. تاریخچه append-only است و در مسیرهای DAO امکان حذف یا بازنویسی رکورد تاریخچه وجود ندارد.

## 3. اتمیک بودن عملیات

- ثبت مشتری و پیشنهاد اولیه موقعیت (در وضعیت PENDING) در یک تراکنش انجام می‌شود؛ در این مرحله هیچ موقعیت جاری ایجاد نمی‌شود.
- تأیید یک پیشنهاد، تغییر وضعیت مشاهده به ACCEPTED و ارتقای آن به موقعیت جاری را در یک تراکنش انجام می‌دهد.
- تأیید اولین موقعیت، بدون تاریخچه انجام می‌شود؛ تأیید موقعیت جایگزین، تغییر موقعیت جاری و افزودن تاریخچه قبلی/جدید را در همان تراکنش انجام می‌دهد.
- رد پیشنهاد فقط وضعیت آن را به REJECTED تغییر می‌دهد و هرگز موقعیت جاری را تغییر نمی‌دهد.
- اصلاح دستی نقطه، پیشنهاد مستقل جدیدی با provider=MANUAL و isManual=true ایجاد می‌کند؛ پیشنهاد GPS اولیه در همان تراکنش REJECTED می‌شود. پیشنهاد دستی نیز تا تأیید صریح کاربر PENDING می‌ماند.
- پیشنهادهای ردشده یا تأییدشده terminal هستند و قابل تغییر وضعیت مجدد نیستند.
- هر شکست در هر یک از عملیات فوق باید کل تراکنش را rollback کند.
- کلیدهای خارجی با رفتار RESTRICT تعریف شده‌اند تا حذف تصادفی مشتری، تاریخچه و مشاهده‌های وابسته را از بین نبرد.

## 4. قرارداد DAO و Repository

- فهرست و جست‌وجوی مشتریان با Flow ارائه می‌شوند.
- جست‌وجو نام فروشگاه، نام مسئول و شماره تماس را بررسی می‌کند و مشتریان غیرفعال را نیز حذف نمی‌کند.
- عملیات نوشتن suspend هستند.
- ثبت مشتری با پیشنهاد اولیه از ایجاد موقعیت جاری جدا است.
- Repository دسترسی مستقل برای ثبت پیشنهاد، ثبت اصلاح دستی، تأیید پیشنهاد و رد پیشنهاد ارائه می‌کند؛ تأیید، مشاهده ذخیره‌شده را به‌روزرسانی می‌کند و آن را دوباره درج نمی‌کند.
- Repository صرفاً مرز دسترسی داده است؛ قواعد دامنه، ارزیابی کیفیت GPS و تشخیص تکراری بودن در این لایه پیاده نمی‌شوند.
- هیچ API برای حذف مشتری ارائه نشده است.

## 5. قیود و موارد باز

- اعتبارسنجی بازه مختصات، نوع مشتری، وضعیت و سازگاری provider/isManual باید در لایه دامنه انجام شود؛ Room به‌تنهایی این قیود معنایی را تضمین نمی‌کند.
- تعیین تکلیف رفتار حذف/پاک‌سازی داده در آینده نیازمند تصمیم محصول است؛ در نسخه اول حذف مشتری وجود ندارد.
- شاخص‌های فعلی برای جست‌وجوی ابتدایی هستند؛ جست‌وجوی مکانی و FTS در گام‌های بعدی طراحی می‌شوند.
- نسخه Schema برابر 1 است. هر تغییر ساختاری آینده باید migration صریح و آزمون migration داشته باشد.
- فایل JSON خروجی Room Schema باید پس از build در مخزن ثبت شود؛ تا پیش از تولید و بازبینی آن، وضعیت schema snapshot برابر NOT COMMITTED باقی می‌ماند.
- آزمون‌های instrumented باید روی emulator اجرا شوند؛ موفقیت build به‌تنهایی آزمون رفتار SQLite را اثبات نمی‌کند.
